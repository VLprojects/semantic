# semantic-ddd

Tactical building blocks of domain-driven design for Kotlin and Java: typed
identifiers, entities, aggregate roots, domain events, business rules and domain
errors. The core is plain Kotlin; JPA, Spring Data and Spring Boot live in
modules of their own.

The contracts of the core are in place; the JPA, Spring Data and Spring Boot
modules are empty so far.

## The core

Packages of `semantic-ddd`, under `pro.vlprojects.semantic.ddd`:

| Package | What is there |
| --- | --- |
| `tactical` | The building blocks, side by side: `DomainObject` they all extend, with `typeName`, the class name in kebab case; `Identifier`, `Identifiable`, `Entity`, `AggregateRoot`, `Versioned`, `AggregateRevision`, `ValueObject`, `Event` with its `EventHeader` and `EventId`, `BusinessRule` |
| `tactical.base` | Base classes to extend, free of any framework: `AbstractEntity` and `AbstractIdentifier` equal by identifier and value, `AbstractAggregateRoot` that registers events, `AbstractEvent` equal by id, and `SimpleEventHeader`, `UuidEventId` and `Revision`, built by `Revision.of(aggregate)` with the class name in kebab case, to fill an event with |
| `dsl` | The ways to write the blocks down: `rule` builds a `BusinessRule`, `check` runs a list of them, `checkRule` checks a one-off condition |
| `architecture.error` | What a layer of the application raises, not a pattern of the model: `DomainException` and the refusals a service extends, `NotFoundException`, `ConflictException`, `BusinessRuleException` |

The strategic patterns, bounded contexts and the like, will get a `strategic`
package of their own.

The contracts are interfaces; `tactical.base` gives classes to extend. What
needs a framework, the mapping of the identifier and the version, proxies and
handing the events out on save, is left to the JPA and Spring Data modules.

The property of `Identifiable` is `identifier`, not `id`: a JPA entity also
implements `Persistable` of Spring Data, and its `getId()` would clash with a
Kotlin `id` (KT-6653).

An event is a header, the revision of its aggregate and fields of its own. The
header, `EventHeader`, holds the id of the event, its name and the time it
happened; the revision, `AggregateRevision`, holds the
name, the identifier and the version of the aggregate. Both are set once when the event
is raised. The event name is stable, not a class name; the aggregate name
comes from the class, `ShoppingCart` is `shopping-cart`, so renaming an
aggregate renames it for the receivers. An event is typed by its aggregate and the identifier of
it, `Event<Cart, CartId>`, so an event cannot name an aggregate of another
type. How an aggregate records its events and hands them out is left to it and
to the adapter that saves it, as Spring Data does with `@DomainEvents`.
`Entity` and `AggregateRoot` take themselves as the first type parameter,
`AggregateRoot<Cart, CartId>`, so that a contract can speak of the concrete
type.

## Modules

![Modules, and which of them a service takes](../docs/assets/modules-light.svg#gh-light-mode-only)
![Modules, and which of them a service takes](../docs/assets/modules-dark.svg#gh-dark-mode-only)

Five artifacts, group `pro.vlprojects.semantic`:

| Artifact | For | Depends on |
| --- | --- | --- |
| `semantic-ddd` | any JVM code: the building blocks | `semantic-vo` |
| `semantic-ddd-jpa` | entities mapped with JPA, with or without Spring | core, `jakarta.persistence-api` |
| `semantic-ddd-spring-data` | Spring Data repositories | the JPA module, `spring-data-commons` |
| `semantic-ddd-spring-boot` | auto-configuration | the Spring Data module, Spring Boot |
| `semantic-ddd-spring-boot-starter` | the usual way in: dependencies only | the four above |

The naming follows the Spring Boot reference: a module of your own is
`<name>-spring-boot`, the starter is `<name>-spring-boot-starter`.
Configuration keys live under `semantic.ddd`.

Directories drop the prefix the path already gives:

```
ddd/
├── core/                  semantic-ddd
├── jpa/                   semantic-ddd-jpa
├── spring-data/           semantic-ddd-spring-data
├── spring-boot/           semantic-ddd-spring-boot
└── spring-boot-starter/   semantic-ddd-spring-boot-starter
```

Packages follow the artifacts: `pro.vlprojects.semantic.ddd`,
`pro.vlprojects.semantic.ddd.jpa`, `pro.vlprojects.semantic.ddd.spring.data`,
`pro.vlprojects.semantic.ddd.spring.boot`.
